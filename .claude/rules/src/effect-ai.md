# Effect AI: the turn loop and tools

The model layer is Effect AI (`LanguageModel`, `Tool`, `Toolkit`, `Prompt`, `AiError` from `effect/unstable/ai`) with `@effect/ai-openrouter` as the provider. Read the installed `.d.ts` before writing against it (`node_modules/effect/dist/unstable/ai/*.d.ts`, `node_modules/@effect/ai-openrouter/dist/*.d.ts`); the `effect` skill has the verified shapes. Vercel AI SDK names (`streamText` options, `maxSteps`, `tool({ inputSchema })`, `useChat`) don't apply here.

## The turn loop is ours

- `LanguageModel.streamText({ prompt, toolkit })` resolves the tool calls of one model step (the stream emits `tool-call` and `tool-result` parts) and stops. It has no step loop. `runTurn` in `src/core/chat.ts` is that loop: when a step finishes with `"tool-calls"`, it appends the step's parts (`Prompt.concat(prompt, Prompt.fromResponseParts(parts))`) and prompts again, up to `MAX_TOOL_STEPS`. Usage and cost are summed across steps, from each step's `finish` part (`part.usage`, and OpenRouter's cost in `part.metadata.openrouter.usage.cost`).
- A turn emits `TurnEvent`s (text deltas, tool calls and results, then one `finish` with the whole reply). `orx ask` renders them as text or NDJSON; the TUI bridge maps them to `UiEvent`s. Add a new kind of event there, not a side channel.
- Retry only before the first part. A step is retried (twice, doubling from 500 ms, or after a rate limit's `retryAfter` when that is at most `MAX_RETRY_AFTER`; longer fails at once) only when nothing has been emitted yet and `isRetryableUpstream(error)` (`src/core/upstream.ts`, the same decision as the `retryable` the user sees): once text reached the user, a retry would repeat it. That's a flag checked inside `Stream.catchIf`, not `Stream.retry` (which re-runs the stream from the start, duplicates output, and ignores the flag).
- An error OpenRouter sends after the stream started arrives as an `error` part (finish reason `"error"`, no `finish` part); `step` fails with an `AiError` whose reason comes from the error's code, the way a status before the stream would map. Finish reason `"error"` without an error part fails too. A `length` or `content-filter` finish ends the turn normally with a `note`.
- A tool name the toolkit doesn't have fails the step before orx sees the call: Effect AI decodes parts against the toolkit, so it's an `InvalidOutputError` (retried before output, a failed turn after). The call never reaches `collected`, so no unanswered call is saved.
- The stream timeout is an idle timeout: `Stream.interruptWhen(watchdog)` fails with `timedOut(...)` once no part has arrived for `MAX_STREAM_SECONDS` while no tool call is running (a bare `Stream.timeout` would end the stream without an error).
- History: each reply stores `steps` (`Prompt.fromResponseParts` per model step, encoded with the Prompt schema) and `toPrompt` replays them verbatim; an interrupted step gets synthetic "interrupted" results for unanswered tool calls (`stepPrompt`). Before each step, `src/core/context.ts` elides old tool outputs when the prompt passes 60% of the model's `context_length`, down to 40%; the turn keeps what it elided (`TurnState.elision`) and extends it only when the prompt passes 60% again, so the steps in between send a byte-identical prefix and keep the provider's prompt cache.
- The toolkit is a parameter: `runTurn({ toolkit })` / `sendMessage(chat, text, model, { toolkit })`, default `defaultToolkit` (`Toolkit.empty`: plain `orx ask` sends no tools).
- `onEnd` (the chat's save, from `sendMessage`) runs exactly once per turn, and nothing else saves. A finished reply is handed to it before the `finish` event goes out (uninterruptibly), so a failed save is the turn's failure (`ChatStore.save` fails `PermissionDenied`, exit 6, when the data dir refuses the write) instead of an error after `ask --json` said `done`. `Stream.onExit` runs `finalize` exactly once however the turn ends (done, failed, interrupted by Ctrl+C, the consumer stopping early): it logs the `llm call` line and, when the turn didn't finish, calls `onEnd` with the reply as far as it got (`interrupted: true`); a failure of that save is logged with `Effect.logError` and never replaces the turn's outcome (130, or the upstream error). A consumer that stops early (the TUI's `iterator.return()`) ends the stream with a `Success` exit, not an interruption, so "didn't finish" can't be read from the exit tag alone; it has to come from whether the final `finish` event was produced.
- Upstream failures are `AiError`s: map them once with `toUpstreamError` (`src/core/upstream.ts`), which decides the message and `retryable` by HTTP status first (for an error sent mid-stream, the code `streamErrorReason` keeps in `metadata.openrouter.errorCode`), then by `error.reason._tag`. By status: 402 (credits, or max_tokens over what the credits cover), 403 (a rejected key, or moderation when OpenRouter's message doesn't mention the key), 404 and 503 (no provider can serve the request) are not retryable; 408 is. By reason: `AuthenticationError`, `ContentPolicyError`, `InvalidRequestError`, and `QuotaExhaustedError` are not retryable; `RateLimitError` is; a tool or schema reason says it's a bug in orx; `InvalidOutputError` says the model's output was invalid, not the network; anything else follows `error.isRetryable`. For a rejected request (`InvalidRequestError` that isn't a 404 or a context-length error) the message includes OpenRouter's reason, capped at 200 characters, because that reason is what the user needs to fix the request (rra does the same). Never show a raw stack, response body, or headers; `detail` (`upstreamDetail`) carries the status and reason for logs.

## Tools

- A tool is `Tool.make(name, { description, parameters, success, failure?, failureMode? })` with Effect Schemas from `src/schemas/tools.ts`, grouped in a `Toolkit` and implemented with `toolkit.toLayer({ name: handler })`. The coding agent's session (bare `orx`, `ask --agent`) sends `SessionTools`: `AgentTools` (`src/tools/agent.ts`, the file and shell tools) plus `SkillTools`; see `agent-tools.md`. Turn-loop tests use a `currentTime` tool that lives only in `tests/helpers/tools.ts`.
- Handlers are Effects that get services from the context (captured with `Effect.context` in `toLayer`), so tests control them. Every tool uses `failureMode: "return"` with the `ToolFailure` schema: input that doesn't decode, or a failed operation, goes back to the model as the result and it can correct itself. Without it, a failure fails the turn.
- The JSON Schema a provider sees comes from `Tool.getJsonSchema(tool)`: objects are open (`additionalProperties: true`), and annotating the tool with `Tool.Strict` doesn't change that (it only sets the `strict` flag in the request OpenRouter receives); an `identifier` annotation on the parameters produces a top-level `$ref` into `$defs`; descriptions and examples come from annotations on the schema before any `.check(...)`, and a custom `Schema.makeFilter` contributes nothing. `@effect/ai-openrouter` then picks a codec transformer by model id: `openai/*` (and `gpt-`, `o1-`, `o3-`, `o4-`) and `anthropic/*` (and `claude-`) ids get the OpenAI or Anthropic rewrite, which closes objects (`additionalProperties: false`) and drops `examples`; every other model gets the open schema. So the same tool reaches different models differently: a description must carry what an example would. Print `Tool.getJsonSchema(tool)` and read it before a model sees a new tool, then pin it in a test.
- The agent's system prompt (`src/core/prompt.ts`) tells the model when to use which tool.

## Tests

Tests run the real provider against the stub OpenRouter (`tests/helpers/stub-openrouter.ts`), the default through `runCli` with `OPENROUTER_BASE_URL` pointed at it. There is no scripted `LanguageModel`: script the stub instead. It can stream `toolCalls` (a queue of `{ name, arguments }`, one per request, each sent as a tool call), `dropAfter` (N text deltas, then drop the connection), `hangAfter` (N deltas, then never finish), `failCompletions` (answer with an error status), `steps` with `error` (a mid-stream error chunk) or `finishReason`, and `replay(names)` recorded fixtures from `tests/fixtures/openrouter/`; `stub.chatRequests` holds the request bodies it received. `tests/openrouter-replay.test.ts` asserts each recorded fixture's text, tokens, and cost through the real provider. Cover: text streaming, a tool call and its follow-up step, the step cap, retry before the first part and no retry after it, the stream timeout saving a partial reply, usage and cost summed across steps, and each `AiError` reason's exit code and `retryable`.
